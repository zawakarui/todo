## Project Overview

This is a vanilla JavaScript TODO application with no build system, bundler, or framework dependencies. The app runs entirely client-side using LocalStorage for persistence and is deployed to GitHub Pages.

## Running the Application

**Local Development:**
```bash
# Simply open the HTML file in a browser
open index.html
```

No build process, compilation, or local server is required. The application runs directly from the file system.

**Testing:**
Open the browser console (F12) and test functionality using the exposed global objects:
```javascript
TodoApp                              // Main app controller
Storage.getAllTasks()                // View all tasks
Storage.getStorageInfo()             // Check storage usage
Task.getStatistics(Storage.getAllTasks())  // Get task stats
```

**Deployment:**
The app is deployed to GitHub Pages from the `master` branch root directory. Any push to master automatically deploys.

## Architecture

### Module Pattern & Data Flow

The codebase uses a **modular object pattern** without ES6 modules. Five global objects form a layered architecture:

```
App (app.js)
  ↓ orchestrates
UI (ui.js) + Filters (filters.js)
  ↓ uses
Task (task.js)
  ↓ uses
Storage (storage.js)
  ↓ interacts with
LocalStorage API
```

**Critical architectural principle:** Data flows downward only. Lower layers (Storage, Task) have no knowledge of upper layers (UI, App). This enables:
- Storage can be tested independently of UI
- Task operations don't trigger DOM updates
- UI re-renders are explicitly controlled by App

### Key Objects and Responsibilities

**Storage (storage.js)** - LocalStorage abstraction layer
- Manages three localStorage keys: `todos`, `todoCategories`, `todoSettings`
- All persistence logic centralized here
- Never manipulates task objects (just stores/retrieves them)
- Handles storage quota errors

**Task (task.js)** - Business logic and validation
- Creates task objects with generated IDs
- Validates task data (title required, max lengths, valid dates)
- Calculates derived properties: `isPastDue()`, `isDueToday()`, `isDueSoon()`
- Never directly accesses localStorage - delegates to Storage
- Pure functions for statistics and formatting

**UI (ui.js)** - DOM manipulation only
- Caches DOM elements in `UI.elements` object at initialization
- All rendering functions are idempotent (can be called repeatedly)
- Escapes HTML to prevent XSS via `escapeHtml()`
- Never modifies data - only renders it

**Filters (filters.js)** - Pure filtering and sorting functions
- All functions return new arrays (no mutations)
- `combineFilters()` applies multiple filters in sequence
- Supports grouping tasks by category, priority, or due date
- Never touches the DOM or localStorage

**App (app.js)** - Event handling and orchestration
- Maintains filter state in `currentFilters` object
- `refreshUI()` is the central UI update function - call this after any data change
- Event delegation on `#task-list` for task operations (checkbox, edit, delete)
- All user interactions flow through App handlers

### Data Model

**Task Object Structure:**
```javascript
{
  id: "timestamp-random",           // Generated by Task.generateId()
  title: "string",                  // Required, max 200 chars
  description: "string",            // Optional, max 500 chars
  category: "string",               // Default: "general"
  priority: "high|medium|low",      // Default: "medium"
  dueDate: "YYYY-MM-DD" | null,    // ISO date string
  completed: boolean,               // Default: false
  createdAt: "ISO timestamp",       // Set on creation
  completedAt: "ISO timestamp" | null  // Set when completed
}
```

**LocalStorage Keys:**
- `todos`: Array of task objects
- `todoCategories`: Array of category strings
- `todoSettings`: Object with `defaultView`, `sortBy`, `theme`

## Common Development Tasks

### Adding a New Task Field

1. Update task object creation in `task.js` → `createTask()`
2. Add validation in `task.js` → `validateTask()`
3. Add form field in `index.html` modal
4. Update `ui.js` → `getFormData()` to read the field
5. Update `ui.js` → `populateForm()` to populate it on edit
6. Update `ui.js` → `createTaskCard()` to display the field

### Adding a New Filter

1. Add filter function in `filters.js` (e.g., `filterByNewCriteria()`)
2. Add filter to `combineFilters()` logic
3. Add UI control in `index.html` control bar
4. Update `App.currentFilters` object to include new filter
5. Add event listener in `app.js` → `setupEventListeners()`
6. Call `App.refreshUI()` when filter changes

### Modifying Storage Structure

**Warning:** Changes to localStorage structure require migration logic. Users' existing data will break if structure changes incompatibly.

Migration pattern:
1. Detect old structure in `storage.js` → `initStorage()`
2. Transform old data to new structure
3. Save transformed data
4. Document migration in commit message

### Styling Changes

The app uses CSS variables defined in `css/styles.css` → `:root` section. Modify these for theme changes:
- Colors: `--color-primary`, `--color-danger`, etc.
- Spacing: `--spacing-xs` through `--spacing-xl`
- Priority colors: `--priority-high`, `--priority-medium`, `--priority-low`

Responsive breakpoints in `css/responsive.css`:
- Mobile: < 768px
- Tablet: 768px - 1023px
- Desktop: ≥ 1024px

## Important Implementation Details

### Event Delegation Pattern

Task list uses event delegation on the container rather than individual handlers per task:
```javascript
// In app.js
document.getElementById('task-list').addEventListener('click', (e) => {
    if (e.target.classList.contains('task-checkbox')) { /* ... */ }
    if (e.target.classList.contains('btn-edit')) { /* ... */ }
});
```

When adding new task actions, add to this delegation handler.

### UI Update Pattern

Always use this pattern after data changes:
```javascript
// Modify data via Task or Storage
const updatedTask = Task.updateTask(id, changes);

// Then update UI
if (updatedTask) {
    App.refreshUI();  // Full refresh
    // OR
    UI.updateTaskCard(updatedTask);  // Targeted update
}
```

Never update the DOM without updating the underlying data.

### Form Modal State

The modal reuses the same form for add and edit modes:
- Add mode: No `data-edit-id` attribute on form
- Edit mode: `data-edit-id` attribute contains task ID
- Check for this attribute in submit handler to determine operation

### Keyboard Shortcuts

Shortcuts are handled in `app.js` → `handleKeyboardShortcuts()`:
- Ctrl/Cmd+N: New task
- Ctrl/Cmd+F: Focus search
- Esc: Close modal

Add new shortcuts by adding cases to this function.

### LocalStorage Limitations

- Size limit: ~5-10MB depending on browser
- Quota exceeded errors are caught in `storage.js` → `saveTask()`
- Private/incognito mode may disable localStorage entirely
- Check `Storage.isAvailable()` before assuming localStorage works
